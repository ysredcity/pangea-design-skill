# 需求规格化（生成前第一步）

> 不论用户输入是「一句话需求」还是「完整 PRD」，**生成任何实际代码之前**，先把它转化为一份**面向界面架构的需求文档**并经用户确认。这一步消除输入颗粒度差异导致的生成质量波动，让「要做哪些页面、怎么组织、每页什么结构与交互」在动手前对齐。

## 目的

- 把任意颗粒度的输入，收敛为结构一致、以**界面架构**为中心的需求文档。
- 对影响架构的模糊点做**有限轮**澄清（参考头脑风暴的「先理解意图、再澄清、后执行」，但克制）。
- 用户确认需求文档后再进入生成，避免「边写边猜、返工」。

## 何时执行

- **执行**：任何「生成 / 新建一个系统、模块、多页面应用，或一个具体页面」的需求。
- **可跳过或极简化**：
  - 在**已确认需求文档**下的续作（继续加一个已说清的页面）；
  - 纯样式 / 文案微调、明确的单点修改（如「把按钮改成次要按钮」）；
  - 用户明确表示「不用确认，直接做」。
- PM demo 模式与开发交付模式**都适用**——需求文档结构一致，差别只在「数据来源」（mock / 既有接口）。

## 澄清原则（参考头脑风暴，但克制）

- **先理解意图再动手**：从输入中先提取「目标用户 / 角色、核心场景、关键实体与数据、主要操作」。
- **只澄清影响界面架构的模糊点**：模块怎么分、有哪些页面、每页主体形态、关键字段/列、角色差异、数据来源、特殊交互结构。与界面架构无关的细节不问。
- **分批、限轮**：把要问的点**一次性打包成一组**问用户，不要挤牙膏。**澄清最多 1–2 轮**；到轮次上限仍不明确的点，用**合理默认假设**补齐，并在需求文档「待确认假设」里显式标注，不再无限追问。
- **能推断就不问**：常规中后台约定（列表要分页、表单要校验、CRUD、空/加载/错误态等）按模板默认，不必确认。
- **不重复问**：用户已说清的不再问；确需信息（如业务字段含义、图标名）才问。

## 澄清问题清单（按需挑选，打包一次问）

仅挑选**对界面架构有实质影响、且用户未说明**的点提问：

- **角色 / 权限**：有哪些使用角色？是否有权限差异导致页面或入口不同？
- **范围 / 模块**：系统大致分哪几块业务域（对应顶部横向模块菜单）？还是单模块即可？
- **页面清单**：核心要哪些页面？每个页面主要做什么？
- **页面形态**：某页面是列表 / 卡片 / 表单 / 详情 / 仪表盘 / 混合？（拿不准就给候选让用户选）
- **关键数据**：列表的主要列、表单的主要字段大致有哪些？（只要主干，不必穷举）
- **数据来源**：demo（mock 数据）还是对接既有接口？
- **特殊交互**：是否涉及分组、锚点、图表、拖拽、审批流、多步骤等特殊结构？

> **产品线也不单独提问**：读需求时顺手匹配[产品专属业务组件](../components-business/README.md)的触发词（如 MSC / 全球营销云中台 / 营销云中台 / 营销中台），命中就在「全局约定」写明 `产品线` 并列出会用到的业务组件；未命中记「通用」。**只有在无法判断时**（只顺带提了一次产品名、或同时提到多个产品）才并进澄清问题里问一句。

> **部署目标不单独提问**：由 agent 按 [deployment.md](deployment.md) 的「环境识别信号表」自动判断并填入需求文档「全局约定」（默认「标准静态」；宿主是飞书 aily / 妙搭 / Coze 或产物需嵌入 iframe 时记为「嵌入式 iframe」）。仅当用户主动提到部署平台、且仍有歧义时，才把它并进这一组问题里顺带确认——**不要为此多占澄清轮次**。

## 命中页面模板时：以模板结构为基准（重要）

需求文档里的「布局结构」**不能凭空设计**。写每个页面之前，先按其「页型」判断是否命中现有页面模板；**一旦命中，该页的布局结构必须以模板文档的「## 页面结构」为基准逐区块照抄**，只允许在此基础上做**明确标注的增补 / 删减**。

否则会出现实测常见问题：需求文档自行设计了一套结构，生成时又去套模板，两边不一致 → 产出与模板样式/布局有偏差。

**做法**：

1. **判断页型 → 命中模板**（对照 [页面生成决策树](../../SKILL.md)）：
   | 页型 | 模板文档 |
   |---|---|
   | 简单列表页 | [page-simple-list.md](../patterns/page-simple-list.md) |
   | 基础列表页 | [page-filter-list.md](../patterns/page-filter-list.md) |
   | 卡片列表页 | [page-card-list.md](../patterns/page-card-list.md) |
   | 基础表单页 | [page-form.md](../patterns/page-form.md) |
   | 分组表单页 | [page-grouped-form.md](../patterns/page-grouped-form.md) |
   | 对话框表单 | [page-modal-form.md](../patterns/page-modal-form.md) |
2. **先读该模板的「## 页面结构」**（以及「设计规范」要点），把区块顺序与构成**原样写进需求文档**该页的「布局结构」——例如简单列表页就是「page-header → 操作栏(filter) → 表格区 → 分页」，不要改名、不要重排、不要遗漏。
3. **增补 / 删减必须显式标注**，让用户一眼看出偏离基准之处：
   - `[基准]` 来自模板的区块；
   - `[增补] xxx`（如额外的统计条、批量操作）；
   - `[删减] xxx`（如本页不需要高级筛选面板）。
4. **匹配度低、确实无模板可用**时，才在需求文档里注明「自定义页型（无模板）」并给出自拟结构；此时仍须遵守全局准则（设计系统组件 + Token + 响应式 + 背景分层）。
5. 生成阶段以需求文档为准，而需求文档已对齐模板 → 三者（模板 / 文档 / 产出）一致。

## 输出：面向界面架构的需求文档

澄清后（或输入已足够可直接推断时），产出如下结构的 Markdown 需求文档，交用户确认。**以界面架构为中心，不写后端 / 技术实现细节**。

```md
# <系统名> 需求文档（界面架构）

## 1. 概述
- 目标用户 / 角色：
- 核心场景（一句话）：
- 数据来源：mock（demo） / 既有接口（开发交付）

## 2. 模块划分（对应顶部横向模块菜单）
- 单模块 / 多模块：<结论及理由>
- 模块列表（多模块时逐个列）：
  - 模块A（key / 标题）：负责……
  - 模块B（key / 标题）：负责……

## 3. 菜单与导航（对应左侧当前模块菜单）
- 模块A 菜单（体现层级 + 路由）：
  - 一级：xxx（/route）
    - 二级：xxx（/route/child）
  - 一级：xxx（/route）
- 模块B 菜单：……

## 4. 页面清单与结构（逐页一节）
### 页面名（/route）
- 页型：简单列表 / 卡片列表 / 基础表单 / 分组表单 / 对话框表单 / 仪表盘 / 自定义
- 套用模板：<模板名，如「简单列表页」；无匹配则写「自定义页型（无模板）」>
- 布局结构：**命中模板时逐区块照抄模板的「## 页面结构」**，自上而下列出并标注 `[基准]` / `[增补] xxx` / `[删减] xxx`
  - 例（简单列表页）：`[基准] page-header` → `[基准] 操作栏(filter)` → `[基准] 表格区` → `[基准] 分页` → `[增补] 顶部统计条`
- 关键内容：列表主要列 或 表单主要字段（主干即可）
- 交互描述：主要操作与结果（新建→弹窗或跳转、行操作、筛选、切 tab、提交校验 …）
- 特殊状态：空 / 加载 / 错误（有特殊要求才写）

## 5. 全局约定
- 产品线：通用（默认） / MSC（全球营销云中台）等——命中产品触发词时注明，并列出会用到的业务组件
- 背景分层：常规页白底 / 仪表板灰底白卡
- 响应式：遵循全局准则（Grid 断点 / 自适应网格）
- 特殊组件 / 图表：如需 VChart 等注明
- 部署目标：标准静态（默认） / 嵌入式 iframe（飞书 aily·妙搭·Coze 等） / History（需服务端 fallback）

## 6. 待确认假设（Assumptions）
- 列出因未澄清而采用的默认假设，便于用户一眼纠正。
```

## 确认闸门（Gate）— 硬停止，禁止同轮继续开发

> ⛔ **这是一道硬门，不是流程建议。** 输出需求文档后**必须结束本轮回复、停下等待用户答复**；**严禁在同一轮里既产出需求文档、又创建 / 修改工程文件**（脚手架初始化、**复制 `templates/project-starter/`**、`degit`、`npm install`、起 dev server、写 `.vue` / 路由 / 菜单都算）。

**阶段一（出文档，本轮结束）**

- 把需求文档发给用户，请其**确认或修改**，重点确认：**模块划分、菜单设定、页面清单、每页布局结构与交互描述**。
- 结尾用一句明确的请求收束，例如：「以上需求文档是否确认？确认后我按此开始生成页面（也可直接指出要改的部分）。」
- 然后**停止**。不要自问自答、不要"顺便先把工程搭起来"、不要预生成任何页面。

**什么算「已确认」**

- ✅ 算：用户**看到需求文档之后**给出的明确肯定答复——「确认」「可以」「按这个做」「没问题，开始」「开发吧」。
- ❌ 不算：用户最初提出需求的那句话；用户回答你的澄清问题；用户说「继续 / 好」但**尚未看到文档**；你自己判断"需求已经很清楚了"。
- 用户提出修改 → 更新文档对应小节后**再次请确认**（仍受「限轮、克制」约束，避免反复拉扯）。

**阶段二（用户确认后的下一轮）**

- 才进入 [页面生成决策树](../../SKILL.md)（按每页「页型」判断套模板 / 增补 / 自主设计）→ 逐页生成 → `vue-tsc` 类型检查 → [生成后质量门禁](quality-gates.md) 自检 → 交付。
- 生成时以已确认文档为准；确需偏离，先说明再改。
- **建议持久化**：把需求文档写入工程 `docs/requirement.md`，作为后续迭代与对照依据（PM demo 模式推荐留存一份）。

**自检（动手写代码前问自己）**

1. 需求文档已经发给用户了吗？
2. 用户在**看到文档之后**明确说可以了吗？
3. 如果任一答案是「否」→ **现在不要写代码**，先补上阶段一。

**反例（错误示范）**：用户说「做一个会议室预约系统」→ 同一轮回复里既写了 `docs/requirement.md`，又生成了 `src/pages/**` 与路由。这违反本门；正确做法是只出文档并请确认。

## 与后续流程的衔接

- 本步骤在**决策树之前**：需求文档中每页的「页型」直接喂给决策树做选型判断；每页的「布局结构 / 关键内容 / 交互」是生成该页的依据。
- **增量迭代**：已确认文档后追加或修改单个页面，直接改文档对应小节 + 生成该页，**不重启整轮规格化**。
- 生成层级仍遵循全局 Layout 铁律（页面是 Layout 子路由；模块划分对应 `GlobalLayout.vue` 的 `modules`，菜单对应各模块 `menu`）。见 [project-structure.md](project-structure.md)。
